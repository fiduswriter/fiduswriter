# Static Assets Distribution & Frontend Unification Plan

**Status:** Implemented  
**Date:** July 2026  
**Context:** The TypeScript/JS code has been extracted into separate npm packages (`@fiduswriter/frontend`, `@fiduswriter/editor`, `@fiduswriter/bibliography-manager`, etc.). CSS files, i18n translations, fonts, and images remain in the main Django app. This plan covers moving those static assets into the appropriate packages and unifying the dependency chain.

**Key architectural principle:** Each package is independently installable and self-contained. If a consumer only needs the editor, they install `@fiduswriter/editor` and get all its CSS, fonts, i18n, and static assets — no dependency on `@fiduswriter/frontend` is required. The `@fiduswriter/frontend` package provides aggregation and SPA chrome for consumers that need the full application shell.

### Deviations from original plan

1. **i18n: msgid-based extraction instead of reference-based splitting.** The `djangojs.po` file was regenerated by Django's `makemessages` after JS source files moved to npm packages, removing active reference comments. The `split-translations.js` reference-based approach was replaced with a msgid-based `extract-i18n-generic.js` script that scans each package's `src/` for `gettext()` calls and looks up translations by msgid (including obsolete `#~` entries preserved by `makemessages`). Django plugin strings (e.g. `fiduswriter-llm`) that don't appear in any npm package's source are correctly excluded.

2. **CSS aggregation via direct copy instead of `dist/css/`.** The planned `@fiduswriter/frontend` postinstall aggregation into `dist/css/` did not work in the transpile environment due to pnpm `file:` protocol snapshot caching. Instead, `base/package.json5` copies CSS directly from each package's `css/` directory. The `aggregate-assets.js` script remains available for standalone use.

3. **Packages kept as direct dependencies for pnpm hoisting.** The plan proposed removing redundant deps from `base/package.json5` since they're transitive through `@fiduswriter/frontend`. However, pnpm does not hoist transitive-only deps to `node_modules/@fiduswriter/<name>/`, breaking postinstall rsync scripts. Therefore `@fiduswriter/editor`, `@fiduswriter/bibliography-manager`, `@fiduswriter/document-template-editor`, and `fwtoolkit` are kept as direct dependencies.

4. **`@fiduswriter/document` and `@fiduswriter/books-document` locale added.** These packages were not in the original i18n scope but contain 99 and 46 gettext calls respectively. Full locale infrastructure was created for both.

### 1.2 i18n Translation Inventory

All translations live in the main Django app's `locale/` directory:

```
locale/
├── ar/   bg/   cs/   da/   de/   en/   en_US/
├── es/   fr/   it/   ja/   ko/   nb/   nl/
├── pl/   pt_BR/  pt_PT/  ru/   sv/   tr/   zh_Hans/
└── copyright.txt
```

Each language directory contains:
- `LC_MESSAGES/django.po` / `.mo` — Python string translations (stay in Django)
- `LC_MESSAGES/djangojs.po` / `.mo` — JavaScript string translations (need to move to npm packages)

The `djangojs.po` files reference exact JS source file paths. Example:
```
#: base/static/js/modules/404/index.js:6
msgid "Page not found"
msgstr "Seite nicht gefunden"
```

Translation loading mechanism:
- Django serves `/api/jsi18n/` which generates a JS catalog at runtime
- The catalog provides `gettext()`, `ngettext()`, `interpolate()` globally
- `fwtoolkit` imports its `gettext` from `src/settings.ts` where it's injected at runtime
- If `gettext` is not injected (standalone), it falls back to identity function (returning msgid unchanged)

No npm package currently has any locale/l10n/i18n files. Exception: `@fiduswriter/books-document` has a `./i18n` export (`src/i18n.ts`) for programmatic helpers.

### 1.5 Current CSS Loading Architecture

The SPA shell template (`base/templates/app.html`) loads CSS via individual `<link>` tags using Django's `{% static %}` template tag:

```html
<!-- Commons styles (from static-libs/css/ — fwtoolkit copies, or base/static/css/ — overrides) -->
<link rel="stylesheet" href="{% static "css/reset.css" %}" />
<link rel="stylesheet" href="{% static "css/colors.css" %}" />
<link rel="stylesheet" href="{% static "css/fonts.css" %}" />
...18 more <link> tags...
```

Django's `{% static %}` resolves to either:
- `static-libs/css/` (where fwtoolkit CSS was copied) — for library CSS
- The Django app's own `static/css/` — for overrides and SPA-specific CSS

Key observations:
- CSS is loaded as **individual files**, not bundled
- No dynamic CSS loading via JavaScript
- The fwtoolkit override pattern (main app's `forms.css` / `colors.css` take precedence over fwtoolkit's versions) works because Django's `{% static %}` resolver finds the local `base/static/css/` file before the `static-libs/css/` copy
- There is no CSS-in-JS, no PostCSS pipeline, no CSS modules

## 2. CSS Distribution Plan

### 2.1 Design Principles

1. **Each package owns its CSS.** The CSS for a component lives in the same npm package as the component's TypeScript code.
2. **Each package is self-contained.** Installing `@fiduswriter/editor` gives you everything needed to render the editor: its CSS, its fonts, its i18n translations, and its static assets. No dependency on `@fiduswriter/frontend` is required for standalone use of individual packages.
3. **CSS overrides are additive layers, not replacement files.** Instead of the current "Django static resolver precedence" hack (where the main app's `colors.css` replaces fwtoolkit's `colors.css`), each package ships CSS files that **add** its own custom properties and rules on top of the fwtoolkit base. The fwtoolkit base files are loaded first, then each package's additive overrides are loaded after. This means the current monolithic override files (`colors.css`, `forms.css`) are **split** so each package owns only the additions it needs.
4. **CSS is deployed as static files, not bundled into JS.** Maintain the current approach of serving CSS as separate `.css` files. This keeps the build simple and allows browsers to cache CSS independently.
5. **Backward compatible.** The main Django app continues to work during the transition.

      "own": {
        "additive": ["colors.css"],

## 3. i18n Translation Distribution Plan

### 3.1 Design Principles

1. **Each package owns its translatable strings.** The `.po` files are split by package based on which source files the strings reference.
2. **Both Django and standalone consumers are supported.** For Django, continue using `/api/jsi18n/`. For standalone, each package ships JSON translations and a small runtime loader.
3. **Fallback to English.** If no translations are available (standalone, no catalog), the `gettext` identity fallback returns the English msgid.
4. **Build-time compilation to JSON.** `.po` files are compiled to `.json` at build time so the runtime doesn't need to parse `.po` format.

### 3.2 Translation File Layout per Package

Each npm package gets:

```
<package>/
├── locale/
│   ├── de/
│   │   ├── messages.po        # Translatable strings from this package
│   │   └── messages.json      # Compiled JSON (shipped in npm package, gitignored)
│   ├── fr/
│   │   ├── messages.po
│   │   └── messages.json
│   └── ... (22 languages)
└── scripts/
    └── compile-i18n.js         # Script: po → json compilation
```

JSON format (`messages.json`):
```json
{
  "": {
    "language": "de",
    "plural-forms": "nplurals=2; plural=(n != 1);"
  },
  "Page not found": "Seite nicht gefunden",
  "Error 404": "Fehler 404",
  "Sending...": "Sendet..."
}
```

### 3.3 Splitting Existing djangojs.po Files

The Django `djangojs.po` files reference source file paths. After the frontend reorganization, most JS files have been moved to npm packages. The `.po` files need to be updated.

**Step 1: Run `makemessages` per package**

Each npm package should use a `makemessages`-compatible tool (like `easygettext` or a custom script) to extract `gettext()` calls from its own TypeScript source into a `messages.pot` template.

**Step 2: Merge existing translations**

For each language, merge the existing `djangojs.po` entries into each package's `messages.po`:
- Match by `msgid` (which is the English string)
- If an entry matches, copy the `msgstr` (translation)
- If no match, leave `msgstr ""` (untranslated — translator needs to fill in)

A script `scripts/split-translations.js` does this:
1. Read the existing `djangojs.po` for a language
2. Parse each package's `messages.pot` template
3. For each `msgid` in the template, look it up in `djangojs.po`
4. Write the merged result to the package's `locale/<lang>/messages.po`

**Step 3: Compile to JSON**

Each package's `compile-i18n` script converts `.po` to `.json` using `gettext-parser` or similar.

### 3.4 Runtime Translation Loading

#### Django Mode (existing, unchanged)

Django continues to serve `/api/jsi18n/`, generated from all packages' `.po` files merged together. The Django `makemessages` command is pointed at all package source directories.

`fwtoolkit`'s injected `gettext` pattern continues to work.

#### Standalone Mode (new)

Each package ships with a small `i18n` runtime:

```typescript
// @fiduswriter/frontend/src/i18n/index.ts

interface TranslationCatalog {
  [msgid: string]: string;
}

class I18n {
  private catalog: TranslationCatalog = {};

  async load(locale: string): Promise<void> {
    // Try to load translations for this locale
    try {
      const module = await import(`../locale/${locale}/messages.json`);
      this.catalog = module.default || module;
    } catch {
      // Fallback: use English (identity function)
      this.catalog = {};
    }
  }

  gettext(msgid: string): string {
    return this.catalog[msgid] || msgid;
  }

  ngettext(singular: string, plural: string, count: number): string {
    const key = `${singular}\0${plural}`;
    const translated = this.catalog[key];
    if (!translated) return count === 1 ? singular : plural;
    // Simple plural handling — full implementation uses plural-forms
    return count === 1 ? translated.split('\0')[0] : translated.split('\0')[1];
  }
}

export const i18n = new I18n();
```

**Translation aggregation in `@fiduswriter/frontend`:**

For standalone mode, `@fiduswriter/frontend` provides an `initI18n(locale)` function that:
1. Loads `@fiduswriter/frontend`'s own translations
2. Loads `@fiduswriter/editor`'s translations
3. Loads `@fiduswriter/bibliography-manager`'s translations
4. Loads `fwtoolkit`'s translations (fwtoolkit currently has no translatable strings in its locale, but its gettext injection point would use this)
5. Merges all catalogs
6. Injects the merged `gettext` function into fwtoolkit via `fwtoolkit.initSettings({gettext})`

The consumer (Django or alternative backend) calls:
```typescript
import { initFrontend } from '@fiduswriter/frontend';

await initFrontend({
  locale: 'de',
  apiConnectors: myApiConnectors,
  // ...
});
```

### 3.5 Translation Tooling

| Tool | Purpose |
|------|---------|
| `easygettext` or `gettext-extractor` | Extract `gettext()` calls from TypeScript source into `.pot` template |
| Custom `split-translations.js` script | Merge existing `djangojs.po` translations into per-package `.po` files |
| `gettext-parser` (npm) | Compile `.po` → `.json` |
| `translate_all.py` (existing) | Automated translation via Google Translate (needs extension for TypeScript packages — see Section 3.6) |

### 3.6 Extending `translate_all.py` for TypeScript Package Locales

The existing `translate_all` management command (in `devel/management/commands/translate_all.py`) uses Google Translate to auto-translate untranslated and fuzzy strings in `.po` files. It currently handles:

- Django's own `locale/` (domains `django` and `djangojs`)
- Plugin locale directories discovered via symlinks under `SRC_PATH`

After the i18n migration, each TypeScript npm package has its own `locale/<lang>/messages.po` files. These packages are **checked out as sibling directories** next to the main fiduswriter repo — they are NOT symlinked into `SRC_PATH` as Django plugins are. The `translate_all` command needs to be extended to discover and translate these TypeScript package locales.

#### 3.6.1 Discovery Strategy

The TypeScript packages live in the parent directory of `SRC_PATH`:

```
<parent>/                         # e.g., /home/user/src/fiduswriter/
├── fiduswriter/                  # Django project (SRC_PATH)
│   └── fiduswriter/              # Django app root (SRC_PATH value)
├── fwtoolkit/                    # TypeScript package
├── fiduswriter-frontend-js/      # TypeScript package
├── fiduswriter-editor-js/        # TypeScript package
├── fiduswriter-document-js/      # TypeScript package
├── fiduswriter-bibliography-manager-js/  # TypeScript package
├── fiduswriter-image-manager-js/         # TypeScript package
├── fiduswriter-document-template-editor-js/ # TypeScript package
└── ...
```

Discovery approach:

```python
# In translate_all.py

def _discover_typescript_package_locales():
    """Find TypeScript package locale directories in sibling directories.

    SRC_PATH is <parent>/fiduswriter/fiduswriter/.
    os.path.dirname(os.path.dirname(SRC_PATH)) is <parent>/.
    """
    parent = os.path.dirname(os.path.dirname(settings.SRC_PATH))
    ts_package_locales = []

    # Known package directory names → nice labels
    KNOWN_PACKAGES = {
        "fwtoolkit": "fwtoolkit",
        "fiduswriter-frontend-js": "@fiduswriter/frontend",
        "fiduswriter-editor-js": "@fiduswriter/editor",
        "fiduswriter-document-js": "@fiduswriter/document",
        "fiduswriter-bibliography-manager-js": "@fiduswriter/bibliography-manager",
        "fiduswriter-image-manager-js": "@fiduswriter/image-manager",
        "fiduswriter-document-template-editor-js": "@fiduswriter/document-template-editor",
        "fiduswriter-books-document-js": "@fiduswriter/books-document",
        "fiduswriter-cli-js": "@fiduswriter/cli",
    }

    for dirname, label in KNOWN_PACKAGES.items():
        locale_dir = os.path.join(parent, dirname, "locale")
        if os.path.isdir(locale_dir):
            ts_package_locales.append((locale_dir, label))
    return ts_package_locales
```

#### 3.6.2 New `--ts-packages` Flag

Add a CLI flag to control TypeScript package translation:

```python
parser.add_argument(
    "--ts-packages",
    nargs="*",
    default=None,
    help=(
        "Names of TypeScript package directories in the parent of "
        "SRC_PATH whose locale files should also be translated. "
        "Use directory names (e.g. fwtoolkit, fiduswriter-editor-js). "
        "If not specified and --no-ts-packages is not set, all known "
        "TypeScript packages with a locale/ subdirectory are "
        "auto-discovered."
    ),
)
parser.add_argument(
    "--no-ts-packages",
    action="store_true",
    help="Skip translation of TypeScript package locales entirely.",
)
```

#### 3.6.3 Domain Mapping

Django locale files use domain-based naming: `django.po`, `djangojs.po`. TypeScript packages use a single `messages.po` per language (equivalent to `djangojs.po` but without the Django-specific domain name). The command needs to handle both naming conventions:

```python
# In the main translation loop:
for locale_root, label in all_locale_dirs:
    for lang in languages:
        lang_dir = os.path.join(locale_root, lang, "LC_MESSAGES")
        if not os.path.exists(lang_dir):
            continue

        if label.startswith("@fiduswriter/") or label == "fwtoolkit":
            # TypeScript package: look for messages.po
            po_files = [
                os.path.join(lang_dir, "messages.po")
            ]
        else:
            # Django app/plugin: look for domain-based .po files
            po_files = [
                os.path.join(lang_dir, f"{domain}.po")
                for domain in domains
            ]
```

#### 3.6.4 Makemessages Integration

Django's `makemessages` cannot scan TypeScript package source directories directly (it expects Django app layouts). The `translate_all` command has `--no-makemessages` flag to skip `makemessages` entirely. For TypeScript packages:

- When `--no-makemessages` is **not** set: the command runs `makemessages` for Django strings as before, but skips it for TypeScript packages (they use their own `npm run extract-i18n` script)
- The command does NOT attempt to run `npm run extract-i18n` in TypeScript packages — that's the developer's responsibility before running `translate_all`
- A warning is printed if a TypeScript package's `.po` files seem stale (i.e., `messages.pot` template is newer than `messages.po`)

#### 3.6.5 Translation Logic Reuse

The core translation logic (`translate_file`, `protect_format_specs`, `restore_format_specs`, `translate_file`) works identically for both Django and TypeScript `.po` files. No changes needed here — `polib` can parse any `.po` file regardless of its origin. The `MAX_CHARS` limit, rate limiting, retry logic, and format specifier protection all apply unchanged.

#### 3.6.6 Example Usage

```bash
# Translate Django strings + all discovered TypeScript packages
python manage.py translate_all --locale de fr

# Translate only fwtoolkit and editor TypeScript packages
python manage.py translate_all --locale de --ts-packages fwtoolkit fiduswriter-editor-js --no-makemessages

# Translate Django strings only (skip TypeScript packages)
python manage.py translate_all --locale de --no-ts-packages

# Translate everything with fuzzy strings excluded
python manage.py translate_all --locale de --no-fuzzy
```

| `bibliography/package.json5` | **Remove.** Handled by `@fiduswriter/frontend` → `@fiduswriter/bibliography-manager`. |
| `usermedia/package.json5` | **Keep `cropperjs` or move to `@fiduswriter/image-manager`.** `cropperjs` is an implementation detail of the image manager. Could either stay here or be pulled in via `@fiduswriter/image-manager`. |
| `browser_check/package.json5` | **Keep.** This is orthogonal (browser check, not part of the frontend framework). |

**Note:** The merge strategy of `django-npm-mjs` (deduplicating identical dependencies across all `package.json5` files) means the existing layout already works correctly. Removing the extra `package.json5` files is a simplification but not strictly necessary. The key win is that installing `@fiduswriter/frontend` (via `base/package.json5`) pulls in everything and the postinstall copies all assets in one step.

### 5.4 Simplified postinstall for Main App

The main Django app's postinstall becomes:

Django's `app.html` template then uses the manifest to generate `<link>` tags instead of hardcoding them.

## 6. CSS Loading Architecture Changes

### 6.1 Django Template Change

**Before:** `app.html` hardcodes ~20 `<link>` tags:
```html
<link type="text/css" rel="stylesheet" href="{% static "css/reset.css" %}" />
<link type="text/css" rel="stylesheet" href="{% static "css/colors.css" %}" />
...
```

**After:** `app.html` uses a Django template tag that reads the CSS manifest:
```django
{% load frontend_css %}
{% frontend_css_links %}
```

The `frontend_css_links` template tag:
1. Reads `static-libs/manifest.json`
2. Iterates through layers in order
3. Emits `<link>` tags with the correct `{% static %}` paths
4. Can optionally support `?v={{ VERSION }}` cache busting

### 6.2 Standalone HTML

For standalone demos and alternative backends, the manifest is read at runtime:

```html
<!-- In a standalone demo page -->
<script type="module">
  import { loadCssFromManifest } from '@fiduswriter/frontend';
  await loadCssFromManifest();
</script>
```

`loadCssFromManifest()`:
1. Fetches the manifest JSON
2. Creates `<link>` elements in the document head for each CSS file
3. Waits for all stylesheets to load (or fails gracefully)

### 6.3 CSS Bundle Option (Future)

For production, an optional build step could concatenate all CSS from a given layer into a single file:

```
dist/css/bundle-reset.css       (Layer 0)
dist/css/bundle-tokens.css      (Layer 1)
dist/css/bundle-typography.css  (Layer 2)
dist/css/bundle-components.css  (Layer 3 + 4)
dist/css/bundle-chrome.css      (Layer 5)
dist/css/bundle-editor.css      (Layer 6)
dist/css/bundle-packages.css    (Layer 7)
```

This reduces HTTP requests while maintaining the loading order. Each layer bundle file can be loaded on demand (e.g., the editor layer is only loaded when the editor page is active). The manifest can reference either individual files or bundles depending on the build mode.

### 6.4 Per-Page CSS Loading (Lazy CSS)

Currently, all CSS is loaded upfront in `app.html`. With the new architecture, page-specific CSS can be loaded lazily. Two approaches exist:

**In the full SPA (via `@fiduswriter/frontend`):**

```typescript
// @fiduswriter/editor/src/index.ts
import { loadCssLayer } from '@fiduswriter/frontend';

export class Editor {
  async init() {
    await loadCssLayer('editor');  // Only loads Layer 6 when editor initializes
    // ... rest of editor init
  }
}
```

**In standalone mode (without `@fiduswriter/frontend`):**

Each package ships its own lightweight CSS loader that reads the `fiduswriter.css` declaration from its `package.json` and generates the correct `<link>` tags:

```typescript
// @fiduswriter/editor/src/load-css.ts (standalone CSS loader)
export async function loadEditorCss(basePath = ''): Promise<void> {
  const links = [
    // Layer 1 — fwtoolkit base tokens
    `${basePath}node_modules/fwtoolkit/css/colors.css`,
    // Layer 3 — fwtoolkit components (subset)
    `${basePath}node_modules/fwtoolkit/css/forms.css`,
    `${basePath}node_modules/fwtoolkit/css/buttons.css`,
    `${basePath}node_modules/fwtoolkit/css/dialog.css`,
    // ... (from package.json fiduswriter.css.fwtoolkit)
    // Layer 4 — Editor additive overrides
    `${basePath}@fiduswriter/editor/css/colors.css`,
    // Layer 6 — Editor components
    `${basePath}@fiduswriter/editor/css/editor.css`,
    `${basePath}@fiduswriter/editor/css/document.css`,
    // ...
  ];

  for (const href of links) {
    const link = document.createElement('link');
    link.rel = 'stylesheet';
    link.href = href;
    document.head.appendChild(link);
  }
}
```

The SPA shell (Layer 0-5) loads immediately. Editor CSS (Layer 6) loads when the editor page opens. Bibliography CSS (Layer 7) loads when the bibliography page opens. This works identically whether the full `@fiduswriter/frontend` is installed or the package is used standalone — the difference is where the CSS loader lives.

## 7. Standalone Package Operation

### 7.1 Goals

1. **Each package is independently installable.** `npm install @fiduswriter/editor` gives you everything: TypeScript code, CSS, fonts, i18n translations, and static assets. No other `@fiduswriter/*` package is required.
2. **Each package can be developed and tested independently.** `npm run dev` in `@fiduswriter/editor` opens a demo page that renders the editor with mock data.
3. **An alternative backend (not Django) can consume any package directly.** Install the packages you need, implement the `ApiConnector` interfaces, and render the component.
4. **The main Django app installs `@fiduswriter/frontend` for the full SPA.** This provides the SPA shell (routing, header menu, feedback tab) plus aggregation of all sub-package assets.
5. **`@fiduswriter/frontend` is a convenience, not a requirement.** You only need it if you want the full SPA chrome and routing. If you just want the editor embedded in your own application, install `@fiduswriter/editor` directly.

**When to use what:**

| Use case | Install | Get |
|----------|---------|-----|
| Full Fidus Writer SPA (Django or alternative backend) | `@fiduswriter/frontend` | SPA shell, all components, aggregated CSS/i18n |
| Embed just the editor in a custom app | `@fiduswriter/editor` | Editor component, its CSS, its i18n |
| Embed just the bibliography manager | `@fiduswriter/bibliography-manager` | Bibliography UI, its CSS, its i18n |
| Embed just the image manager | `@fiduswriter/image-manager` | Image manager UI, its CSS, its i18n |
| Use fwtoolkit components in your own app | `fwtoolkit` | UI toolkit, its CSS |

### 7.2 Per-Package Demo Infrastructure

Each package gets a `demo/` directory that works **without** `@fiduswriter/frontend`:

```
@fiduswriter/editor/
├── demo/
│   ├── index.html       — Standalone HTML shell
│   └── demo.ts          — Entry point, initializes editor with mock data
├── css/                 — Editor's own CSS (additive + component)
└── locale/              — Editor's own translations
```

All CSS and fwtoolkit dependencies are loaded directly from the package's own `node_modules`, not from an external aggregator.

### 7.3 Alternative Backend Contract

For an alternative backend to use the Fidus Writer frontend:

```typescript
import { initFrontend, App } from '@fiduswriter/frontend';

const app = new App({
  locale: 'en',
  apiConnectors: {
    // Implement the ApiConnector interfaces from @fiduswriter/frontend/src/api/
    document: new MyDocumentConnector(),
    bibliography: new MyBibliographyConnector(),
    user: new MyUserConnector(),
    usermedia: new MyUsermediaConnector(),
    // ...
  },
  settings: {
    staticUrl: (path) => `/assets/${path}`,
    getCsrfToken: () => document.querySelector('meta[name=csrf]')?.content,
  },
  container: document.getElementById('app'),
});

await app.start();
```

The `ApiConnector` interfaces (already defined in `@fiduswriter/frontend/src/api/index.ts`) are the contract. Any backend that implements these interfaces can use the frontend.

### 7.4 fwtoolkit Initialization

For standalone operation, each package initializes `fwtoolkit` with its own settings. This works identically whether or not `@fiduswriter/frontend` is installed.

**Standalone editor example (no `@fiduswriter/frontend`):**

```typescript
// @fiduswriter/editor/demo/demo.ts
import { initSettings } from 'fwtoolkit';

// fwtoolkit requires gettext to be injected. In standalone mode,
// load the editor's own translations and provide gettext.
import { loadTranslations, gettext } from '@fiduswriter/editor/i18n';

async function main() {
  await loadTranslations('en');  // load @fiduswriter/editor/locale/en/messages.json
  initSettings({
    staticUrl: (path) => `/static/${path}`,
    getCsrfToken: () => null,
    gettext: (msgid) => gettext(msgid),
  });
  // Now fwtoolkit components render with translations
}
```

**Full SPA example (with `@fiduswriter/frontend`):**

```typescript
// consumer app
import { initFrontend } from '@fiduswriter/frontend';

await initFrontend({
  locale: 'de',
  apiConnectors: myApiConnectors,
  container: document.getElementById('app'),
});
// initFrontend handles fwtoolkit initialization internally
```

In both cases, the same `fwtoolkit.initSettings()` call happens. The difference is whether the consumer calls it directly or `@fiduswriter/frontend` calls it as part of `initFrontend()`. This is important because `fwtoolkit` stores app settings in module-local state — it must only be initialized once, and all packages in the same JS runtime share that one initialization.

## 9. Risks and Mitigations

| Risk | Impact | Mitigation |
|------|--------|------------|
| **CSS loading order regression** | Visual breakage if CSS loads in wrong order | Extensive visual regression testing. The CSS manifest enforces correct order. |
| **Font path breakage** | Missing fonts (fallback to system fonts) | Test font rendering across browsers. Keep old paths as fallback. |
| **Translation loss** | Missing translations, English strings shown | Run automated comparison: for each language, compare old `djangojs.po` msgid set with new per-package msgid set. Report gaps. |
| **`django-npm-mjs` merge issues** | Duplicate dependencies, wrong versions | Test with clean `pnpm-lock.yaml` and `node_modules/`. Use `pnpm why` to verify deduplication. |
| **`fwtoolkit` version mismatch** | Two different fwtoolkit versions in the bundle → "App settings not initialized" error | Critical. Ensure all packages depend on the same `fwtoolkit` version. Use `pnpm.overrides` in the main app if needed. |
| **Standalone i18n performance** | Loading 22 language JSON files at startup | Load only the requested locale. Use dynamic `import()`. Cache in `localStorage`. |
| **Postinstall script fragility** | Asset aggregation breaks on package updates | Use explicit, tested paths. Fail loudly on missing files. Add CI test that verifies postinstall output. |
| **Django static file resolution changes** | `collectstatic` picks up wrong files | Explicitly configure `STATICFILES_DIRS` to point at the correct directories. |

## 10. Key Decisions Log

| Decision | Rationale |
|----------|-----------|
| **Each package is self-contained and independently installable** | `@fiduswriter/editor` is usable without `@fiduswriter/frontend`. This keeps packages lightweight for consumers that only need one component (e.g., embedding the editor in a custom app). |
| CSS stays as plain `.css` files, not bundled into JS | Maintains simplicity, independent caching, and the existing mental model |
| CSS override pattern: additive layers, not replacement files | Each package adds its own custom properties/rules on top of fwtoolkit base. No monolithic override files. Enables self-contained packages. |
| CSS dependency declarations in `package.json` (`fiduswriter.css` key) | Machine-readable, used by both the `@fiduswriter/frontend` aggregator and standalone package demo generators. |
| CSS manifest is generated, not hand-written | Avoids duplication and drift. The manifest is built from each package's `fiduswriter.css` declaration. |
| Translation format: `.po` (source) + `.json` (compiled) | `.po` is already used by Django and translators. `.json` is easy to consume in standalone mode |
| `gettext` identity fallback for missing translations | Graceful degradation: English msgid is shown when no translation is available |
| `@fiduswriter/frontend` as convenience aggregator for full SPA | Simplifies setup for the main Django app and full-SPA alternative backends. Not required for individual packages. |
| Keep Django `django.po` (Python strings) separate from `messages.po` (JS strings) | Python translations stay in Django's `locale/`. JS translations move to npm packages. |
| CSS layers for lazy loading | Allows editor CSS to load only when editor page is active, reducing initial CSS payload |

## 11. Open Questions

1. **`fwtoolkit` translations — DECIDED:** fwtoolkit will get its own `locale/` directory with `.po` files. This is confirmed — fwtoolkit is a standalone library used by other consumers (not just Fidus Writer), so its translations belong in its own package. The `gettext` injection pattern already supports this: fwtoolkit just needs its translations loaded and its `gettext` function configured at init time. The `translate_all` command (see Section 3.6) will discover and translate fwtoolkit's locale files alongside the other TypeScript packages.

2. **Document export CSS (`document/static/css/document.css` vs `@fiduswriter/document/src/css/document.css`):** Are these different files? If so, which one is used for what?

   *Recommendation:* Audit both files. The `@fiduswriter/document` version is for HTML/EPUB export output. The `document/static/css/document.css` in the main app might be for the editor's preview or for editor document styling. If they serve different purposes, keep both in their respective packages. If they overlap, consolidate.

3. **Browser-specific CSS:** Are there any browser-specific CSS hacks (IE, Safari, Firefox) in the existing files?

   *Recommendation:* Audit during Phase 1. If found, document them and ensure they're preserved.

4. **CSS custom property fallbacks:** Some CSS files might use `var(--custom-prop, fallback)`. Are these fallback values consistent?

   *Recommendation:* Not a blocker. The layered loading order (fwtoolkit defaults → `@fiduswriter/frontend` overrides) ensures custom properties are defined before use.

5. **Should `@fiduswriter/frontend` re-export CSS from its dependencies, or should consumers import CSS from each package directly?**

   *Decision:* Each package ships its own CSS directly. `@fiduswriter/frontend` aggregates CSS for the convenience of full-SPA consumers. Standalone consumers get CSS from the package they install (e.g., `@fiduswriter/editor` ships its own `css/` directory).

6. **CSS override overlap:** When a consumer installs multiple standalone packages (e.g., `@fiduswriter/editor` + `@fiduswriter/bibliography-manager` without `@fiduswriter/frontend`), each package's additive `colors.css` adds its own custom properties. Since these are additive (not replacement), they compose correctly — no conflict. However, the consumer must ensure fwtoolkit CSS (the base layer) is loaded only once.

   *Recommendation:* Each standalone package's CSS loader should be idempotent — it checks if fwtoolkit CSS is already loaded before adding `<link>` tags. This is a minor implementation detail for each package's `loadCss()` function.
